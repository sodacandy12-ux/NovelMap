# 소설 지도 (Novel Map) 기획 문서

Oct 11, 2026 · @사용자

## 프로젝트 개요

소설 지도는 원고를 올리면 인물 관계도, 사건 타임라인, 로어북(설정집)을 자동으로 만들어 한 화면에서 탐색하고 마크다운으로 내려받게 해주는 작가용 분석 도구다.

장편을 쓰다 보면 인물 관계, 사건 순서, 각종 설정이 작가의 기억에만 남아 설정 충돌과 누락이 생긴다. 소설 지도는 원고 전체를 읽고 이 세 가지를 지도와 설정집으로 정리한다.

- 타깃 사용자: 웹소설·장편 작가, 편집자, 시연을 보는 개발자 관객
- 핵심 가치 1: 설정집 없이 원고만으로 지도와 로어북이 만들어진다.
- 핵심 가치 2: 지도의 모든 점과 선이 원문 근거 장면으로 연결된다.
- 핵심 가치 3: 질문하면 답과 함께 지도의 해당 부분이 하이라이트된다.
- 기술 축: RAG(장면 검색), LangGraph(추출·검증 파이프라인), FastAPI(분석·조회 API), 공급사 선택형 LLM API, Neo4j(관계 그래프)

## 목표와 범위

4일 안에 샘플 소설 1편을 끝까지 분석해 관계도·타임라인 두 가지 지도, 로어북, 질의응답을 시연할 수 있는 수준으로 만드는 것이 목표다.

샘플은 저작권이 만료된 『바스커빌가의 개』(영문 원문, 약 6만 단어, 15개 장)를 기본안으로 한다. 분석 결과와 화면 텍스트는 한국어로 보여준다.

**만들 것 (In scope)**

- 원고 업로드(txt)와 장면 단위 분할·인덱싱(장 구분이 없는 원고 포함)
- 인물 관계도(확대·축소·이동 지원), 사건 타임라인(세로 = 장면 순서, 가로 = 장소 레인) 지도 2종
- 온톨로지 정의(ontology.yaml)와 Neo4j 그래프 적재
- 관계 경로 찾기: 두 인물 사이의 최단 관계 경로 조회
- 로어북 카드 갤러리: 인물·장소·조직·물건·용어를 분류별 카드로 정리
- 로어북 마크다운 내보내기(.md 다운로드)
- LLM 설정 바: 공급사·모델 드롭다운과 API 키 입력창
- 노드·엣지·카드 클릭 시 근거 장면 원문 표시
- 지도 기반 질의응답(RAG): 장면 검색에 그래프 이웃 정보를 더하는 GraphRAG 방식
- 분석 결과 JSON 캐시: 시연 중 재분석 없이 즉시 로딩

**만들지 않을 것 (Out of scope)**

- 로그인, 다중 사용자, 프로젝트 저장 관리
- 원고 편집기와 실시간 설정 충돌 검수
- 복선 회수 판정: 정확도 문제로 후속 확장으로 미룸
- 모바일 화면 최적화
- 10만 단어를 넘는 대용량 원고
- API 키의 영구 저장과 사용자별 키 관리: 키는 서버 메모리에만 둔다
- 로컬 LLM(LM Studio 등) 연동: 외부 API 호출 방식만 지원한다
- 이야기 속 시간순 정렬(플래시백 보정): 타임라인은 원고 순서만 지원한다
- LLM이 직접 Cypher를 생성하는 질의: 확장 항목으로 미룸

**성공 기준 (목표치, 개발하며 조정)**

- 샘플 원고 전체 분석이 10분 이내에 끝난다.
- 주요 인물 10명 이상, 관계 15개 이상이 지도에 나타난다.
- 로어북 항목이 30개 이상 만들어지고, 모든 속성에 근거 장면이 붙는다.
- 지도와 로어북의 모든 요소에서 근거 장면을 1개 이상 열 수 있다.
- 내려받은 마크다운 파일이 열리고 분류별 항목이 비어 있지 않다.
- 설정 바에서 API 키를 넣으면 연결 테스트가 통과하고, 키가 없으면 분석이 시작되지 않는다.
- Neo4j에 인물·관계가 적재되고, 두 인물 사이의 최단 경로가 조회된다.
- 타임라인이 장 구분이 없는 원고에서도 장소 레인으로 표시된다.
- 관계도에서 전체 보기를 켜도 확대·축소와 화면 이동으로 모든 인물 노드를 확인할 수 있고, 6가지 관계 선을 색과 모양으로 구분할 수 있다.

## 핵심 기능

기능은 지도 2종, 관계 경로 찾기, 로어북, 마크다운 내보내기, LLM 설정, 질의응답이며, 모두 같은 근거 장면 패널을 공유한다. 앞의 여섯 가지가 없으면 시연이 성립하지 않아 P0, 질의응답은 일정에 여유가 있을 때 붙이는 P1이다.

| 기능 | 화면에서 보이는 것 | 추출하는 데이터 | 우선순위 |
| --- | --- | --- | --- |
| 인물 관계도 | 인물 노드(크기 = 등장 장면 수)와 관계 선(색 = 관계 대분류 6종, 호버 = 세부 라벨), 확대·축소·화면 이동 | 인물, 별칭, 관계 대분류·세부 라벨·방향, 관계가 바뀐 시점(장면) | P0 |
| 관계 경로 찾기 | 관계도에서 두 인물을 고르면 둘 사이의 최단 경로를 강조 | Neo4j에 적재된 인물 노드와 관계 | P0 |
| 사건 타임라인 | 세로 = 장면 순서, 가로 = 장소 레인으로 놓인 사건 카드, 인물을 고르면 동선 선 | 사건 요약, 등장인물, 사건 장소(장소 항목), 장면 순서 | P0 |
| 로어북 카드 | 분류별 필터와 검색이 되는 카드 갤러리, 카드 상세(속성, 요약, 근거 장면) | 인물·장소·조직·물건·용어의 이름, 별칭, 속성, 요약, 등장 장면 | P0 |
| 마크다운 내보내기 | 로어북 탭의 내려받기 버튼 | 로어북 전체를 분류별 .md 파일로 변환 | P0 |
| LLM 설정 | 상단 설정 바: 공급사 드롭다운, 모델 드롭다운, API 키 입력창 | 공급사, 모델, API 키(서버 메모리에만 보관) | P0 |
| 지도 질의응답 | 채팅창과, 답변에 쓰인 노드·카드의 하이라이트 | 장면 임베딩 검색 결과, 그래프 이웃 정보, 인용 장면 | P1 |

**근거 장면 패널 (공통)**: 지도 요소나 로어북 카드를 눌러도 우측 패널에 원문 장면이 열리고, 근거가 된 문장이 강조된다. 로어북 속성에는 근거 장면 링크가 붙어 있어 누르면 해당 문장이 강조된다. 이 패널이 "AI가 지어낸 지도가 아니다"를 증명하는 장치다.

## 로어북 설계

로어북은 장면별 추출 결과를 대상(인물·장소·조직·물건·용어)별로 모아 카드로 만들고, 같은 데이터를 마크다운 설정집으로 내보내는 기능이다. 모든 속성에 근거 장면 ID가 붙는 것이 원칙이다.

**카드 구성**

| 필드 | 내용 | 생성 방식 |
| --- | --- | --- |
| 분류 | 인물, 장소, 조직, 물건, 용어 중 하나 | 장면별 추출에서 LLM이 분류 |
| 이름·별칭 | 대표 이름과 별칭 목록 | 정규화 노드에서 병합 |
| 속성 | 나이, 직업, 외모, 소속 같은 키-값과 근거 장면 ID | 장면별 추출, 근거 ID가 없으면 검증에서 제거 |
| 요약 | 3\~5줄 설명 | 로어북 생성 노드에서 LLM이 작성 |
| 첫 등장·등장 장면 수 | 장면 ID와 횟수 | 코드로 계산, LLM 호출 없음 |
| 함께 나온 항목 | 같은 장면에 등장한 다른 카드 링크 | 코드로 계산, LLM 호출 없음 |

**생성 순서**

1. 장면별 추출: 항목 후보와 속성을 근거 장면 ID와 함께 받는다.
2. 정규화: 별칭을 병합해 같은 대상을 한 항목으로 합친다.
3. 로어북 생성: 대상별로 속성을 모으고, 장마다 달라지는 값(직함 변화 등)은 둘 다 남긴 뒤 3\~5줄 요약을 쓴다.
4. 검증: 근거 장면 ID가 실제로 있는지 확인하고, 근거 없는 속성은 제거한다.

요약이 원문에 없는 내용을 지어낼 수 있으므로, 요약 입력은 해당 대상의 속성과 장면 발췌로 제한하고 프롬프트에 "근거 장면에 없는 내용 금지" 규칙을 넣는다.

**마크다운 내보내기**

GET /novels/{id}/lore/export가 분류별 H2, 항목별 H3, 속성 불릿으로 정리한 .md 파일을 돌려준다. 속성 뒤에는 근거 장면 ID를 괄호로 남겨 설정집에서 원문으로 되돌아갈 수 있게 한다. JSON을 문자열 템플릿으로 바꾸는 코드라서 LLM 호출이 없다.

```markdown
# 로어북: 바스커빌가의 개

## 인물

### Sherlock Holmes
- 별칭: Holmes
- 직업: 탐정 (s0001)
- 첫 등장: s0001 · 등장 장면 수: 12

(요약 3~5줄)

## 장소

### Baskerville Hall
- 속성: ... (s0042)
```

위 값은 형식을 보여주는 예시다.

## 온톨로지와 그래프 설계

온톨로지는 소설 세계에 어떤 종류의 대상과 관계가 있는지 미리 정해 둔 분류 체계다. 이 프로젝트는 그 정의를 ontology.yaml 한 파일에 두고, 추출 프롬프트·검증 노드·Neo4j 적재가 모두 이 파일을 따르게 한다. 관계를 따라가는 질문(두 인물 사이의 경로, 이웃 확장)은 Neo4j가 맡는다.

**노드 클래스**

| 클래스(Neo4j 레이블) | 의미 | 주요 속성 |
| --- | --- | --- |
| Character | 인물 | id, name, aliases, first\_scene |
| Place | 장소 | id, name, aliases |
| Organization | 조직 | id, name, aliases |
| Item | 물건 | id, name, aliases |
| Term | 용어 | id, name, aliases |
| Event | 사건 | id, summary |
| Scene | 장면 | scene\_id, order |

인물·장소·조직·물건·용어는 로어북 분류와 같고, 로어북 속성(attributes)은 JSON 문자열 속성으로 저장한다. 원문 텍스트는 그래프에 넣지 않고 Chroma와 JSON을 참조한다.

**관계 타입**

| 관계 타입 | 방향 | 의미와 속성 |
| --- | --- | --- |
| FAMILY, ROMANCE, ALLY, HIERARCHY, HOSTILE, OTHER | Character → Character | 인물 관계 대분류 6종(가족, 연애·혼인, 협력·동료, 위계·소속, 적대·갈등, 기타·중립). 속성: label, directed, since\_scene, evidence\_scene\_ids |
| PARTICIPATED\_IN | Character → Event | 사건 참여 |
| OCCURRED\_AT | Event → Place | 사건이 일어난 장소, 타임라인 가로축(레인)의 근거 |
| IN\_SCENE | Event → Scene | 사건이 나온 장면, 타임라인 세로축의 근거 |
| MENTIONED\_IN | 로어북 항목 → Scene | 등장 장면, 근거 장면 링크의 근거 |

directed가 false인 관계는 질의에서 방향을 무시한다.

**ontology.yaml 예시**

```yaml
classes: [Character, Place, Organization, Item, Term, Event, Scene]
relations:
  FAMILY:    {from: Character, to: Character, label_ko: 가족}
  ROMANCE:   {from: Character, to: Character, label_ko: 연애·혼인}
  ALLY:      {from: Character, to: Character, label_ko: 협력·동료}
  HIERARCHY: {from: Character, to: Character, label_ko: 위계·소속}
  HOSTILE:   {from: Character, to: Character, label_ko: 적대·갈등}
  OTHER:     {from: Character, to: Character, label_ko: 기타·중립}
  PARTICIPATED_IN: {from: Character, to: Event}
  OCCURRED_AT:     {from: Event, to: Place}
  IN_SCENE:        {from: Event, to: Scene}
  MENTIONED_IN:    {from: [Character, Place, Organization, Item, Term], to: Scene}
```

**Cypher 질의 예시**

```cypher
// 두 인물 사이의 최단 관계 경로 (관계 경로 찾기)
MATCH p = shortestPath(
  (a:Character {id: $source_id})-[:FAMILY|ROMANCE|ALLY|HIERARCHY|HOSTILE|OTHER*..6]-(b:Character {id: $target_id})
)
RETURN p

// 한 인물과 적대 관계로 2단계 이내에 닿는 인물
MATCH (a:Character {id: $id})-[:HOSTILE*1..2]-(b:Character)
RETURN DISTINCT b
```

**적재와 질의 방식**

- JSON 캐시가 기본 데이터이고, Neo4j는 같은 데이터를 그래프로 한 번 더 저장한 사본이다. Neo4j 없이도 지도·로어북·타임라인은 동작한다.
- 검증 노드가 ontology.yaml에 없는 클래스·관계 타입을 제거하고, 관계는 양쪽 인물이 모두 있을 때만 통과시킨다.
- 적재는 결과 저장 노드가 id 기준 MERGE로 수행하므로 재실행해도 중복되지 않는다.
- Neo4j 접속 정보(NEO4J\_URI, NEO4J\_USER, NEO4J\_PASSWORD)는 .env 환경 변수로만 받고 설정 바에는 넣지 않는다. API 키와 같은 규칙으로 로그와 Git에 남기지 않는다.
- 관계 경로 찾기: 인물 두 명을 고르면 위 Cypher 템플릿으로 최단 경로를 조회한다. LLM 호출이 없다.
- GraphRAG 질의응답: 질문에서 인물·장소 이름을 찾아 Neo4j에서 1\~2단계 이웃과 관계의 근거 장면을 가져오고, 벡터 검색으로 찾은 장면과 함께 LLM에 준다. LLM이 Cypher를 직접 만드는 방식은 정확도 검증이 필요해 확장 항목으로 뒀다.
- Neo4j가 연결되지 않으면 경로 찾기는 비활성화되고, 질의응답은 벡터 검색만 사용한다.

## 시스템 아키텍처

시스템은 인덱싱과 분석 두 파이프라인으로 나뉘고, 둘 사이를 벡터DB(Chroma)가 잇는다.

업로드하면 인덱싱 파이프라인이 장면을 벡터DB에 넣고, 분석을 시작하면 LangGraph가 그 장면을 읽어 추출·검증한 결과를 JSON 캐시에 저장한다. 조회 API는 이 JSON을 그대로 돌려주고, 질문 API만 Chroma를 직접 검색한다. 분석(LLM 호출)과 조회를 분리해 두면 시연 중에는 캐시만 읽어 안정적으로 동작한다. LLM 호출은 설정 바에서 고른 외부 API로 나가고, 캐시를 읽는 조회에는 API 키가 필요 없다.

## LLM 연동 설계

분석과 질의응답의 LLM 호출은 공급사 어댑터 하나를 거치고, 공급사·모델·API 키는 화면 상단의 설정 바에서 고른다. 기본값은 Claude Haiku 5.5다.

**공급사와 모델**

| 공급사 | 모델 | 구현 우선순위 |
| --- | --- | --- |
| Anthropic | Claude Haiku 5.5(claude-haiku-5-5)가 기본값, 어려운 판정용으로 Sonnet 5.5(claude-sonnet-5-5) 선택 가능 | P0, 가장 먼저 구현 |
| OpenAI | 모델 ID는 models.json에 적는다 | P1, 같은 인터페이스로 추가 |
| Google | 모델 ID는 models.json에 적는다 | P1, 같은 인터페이스로 추가 |

모델 목록은 코드가 아니라 models.json에서 읽고, 모델 ID는 각 공급사의 공식 문서를 확인해 채운다. 아직 구현하지 않은 공급사는 드롭다운에서 "준비 중"으로 비활성 표시한다.

**어댑터 인터페이스**

- 노드는 공급사를 모른다. 모든 호출은 generate\_json(prompt, schema) 하나를 거치고, 결과는 Pydantic으로 검증한다.
- 공급사마다 다른 구조화 출력 방식, 재시도, 오류 형식은 어댑터 안에서 처리한다.
- Haiku 5.5는 temperature 같은 샘플링 파라미터를 보내면 오류가 나므로 생략한다. 기본으로 켜진 adaptive thinking은 추출 노드에서 effort를 낮추거나 꺼서 속도와 비용을 줄인다.
- 병렬 호출 수는 설정값으로 제한하고, 429 응답은 지수 대기 후 재시도한다.
- 임베딩은 LLM과 분리해 로컬 bge-m3를 쓰므로, 공급사를 바꿔도 인덱스를 다시 만들 필요가 없다.

**설정 바 동작**

1. 공급사 드롭다운을 고르면 모델 드롭다운이 그 공급사의 목록으로 바뀐다(GET /llm/providers).
2. API 키 입력창에 키를 넣고 저장하면 PUT /llm/config로 한 번 전송되고, 서버가 연결 테스트를 1회 하고 성공 여부를 돌려준다.
3. 성공하면 입력창이 마스킹 표시로 바뀌고 분석 시작 버튼이 켜진다. 키가 없으면 버튼은 꺼져 있다.
4. 서버 환경 변수에 키가 있으면(예: ANTHROPIC\_API\_KEY) 입력 없이 그 값을 기본으로 쓴다.

**API 키 처리 규칙**

- 입력창은 비밀번호 형식이며, 키는 요청 본문으로만 보내고 URL 쿼리에는 싣지 않는다.
- 서버는 키를 메모리에만 두고, 파일·로그·JSON 캐시·LangGraph State에 쓰지 않는다. 서버를 재시작하면 다시 입력한다.
- 저장한 뒤에는 키 전체를 화면에 다시 보여주지 않는다.
- localhost에서 쓰는 전제다. 외부에 배포하려면 HTTPS와 사용자별 키 관리가 필요하고, 이번 범위 밖이다.
- 키를 .env에 둘 때는 .gitignore에 넣는다.

## LangGraph 설계

분석은 장면 로드 → 추출 → 정규화 → 로어북 생성 → 검증 → 저장의 6개 노드이고, 검증이 실패할 때만 추출로 돌아가는 조건부 엣지가 하나 있다.

&#91;embedded content: LangGraph 분석 흐름 · 6개 노드, 재시도 루프 1개\]

검증 노드는 Pydantic 스키마와 근거 장면 ID의 실존 여부를 확인하고, 근거 없는 로어북 속성은 제거한다. 실패하면 retry\_count를 올려 추출로 되돌리고, 2회를 넘기면 실패 항목에 "근거 부족" 표시를 붙여 저장 단계로 넘긴다. 장면별 추출은 장면 수만큼 병렬로 실행한다(LangGraph의 Send로 팬아웃).

검증 노드는 온톨로지 파일(ontology.yaml)에 없는 클래스나 관계 유형을 걸러내고, 관계는 양쪽 인물이 모두 존재할 때만 통과시킨다. 결과 저장 노드는 JSON 캐시를 쓴 뒤 Neo4j가 연결돼 있으면 같은 데이터를 그래프로 적재한다. Neo4j가 없어도 지도와 로어북은 JSON만으로 동작한다.

**상태(State) 정의**

```python
class AnalysisState(TypedDict):
    novel_id: str
    scenes: list[Scene]                  # 장면 로드 결과 (order 순)
    extractions: list[SceneExtraction]   # 장면별 추출 원본
    characters: list[Character]          # 정규화 후 인물
    relations: list[Relation]
    events: list[Event]
    lore_entries: list[LoreEntry]        # 로어북 항목(요약 포함)
    errors: list[str]                    # 검증 실패 사유
    retry_count: int                     # 재시도 횟수, 최대 2
```

**조건부 엣지**

```python
def route_after_check(state: AnalysisState) -> str:
    if not state['errors']:
        return 'save'
    if state['retry_count'] < 2:
        return 'extract'
    return 'save'  # 2회 넘으면 실패 항목을 표시하고 저장
```

## RAG 및 데이터 설계

원고는 장면 단위로 쪼개(장 구분이 있으면 장 안에서) 벡터DB에 넣고, 추출 결과는 근거 장면 ID를 반드시 달고 있는 JSON 엔티티로 정규화한다. 이 장면 ID가 시각화에서 원문으로 돌아가는 링크의 원천이다.

**청킹 전략**

- 1차 분할: 빈 줄·구분선·장 제목(있을 때만) 기준으로 장면을 나눈다. 장 구분이 없는 원고도 같은 방식으로 처리한다.
- 크기 보정: 장면이 600토큰을 넘으면 문단 경계에서 자르고, 150토큰 미만이면 앞 장면에 합친다.
- 메타데이터: scene\_id(예: s0042, 전체 순번 기반), order(전체 순번), chapter(장 구분이 있을 때만, 없으면 비움), prev\_id, next\_id를 저장한다. order는 타임라인 세로축 기준이고, prev/next는 인접 장면 확장 검색에 쓴다.
- 저장소: Chroma(로컬, 설치 간단), 임베딩은 로컬 다국어 모델 bge-m3를 쓴다(공급사와 무관하게 API 키 없이 동작).

**추출 결과 스키마**

| 엔티티 | 주요 필드 | 지도·로어북에서의 역할 |
| --- | --- | --- |
| Character | id, name, aliases\[\], first\_scene, scene\_count | 관계도 노드 |
| Relation | source, target, type, label, directed, since\_scene, evidence\_scene\_ids\[\] | 관계도 선 |
| Event | id, summary, scene\_id, characters\[\], location\_id(장소 항목 id) | 타임라인 카드 |
| LoreEntry | id, category, name, aliases\[\], attributes\[{key, value, evidence\_scene\_ids\[\]}\], summary, first\_scene, scene\_count | 로어북 카드, 마크다운 내보내기 |

별칭 통합("Holmes"와 "Mr. Sherlock Holmes"를 한 인물로)은 추출 후 정규화 노드에서 처리한다. 정규화 없이는 관계도에 같은 인물이 여러 개 생겨 시연이 무너진다.

로어북의 인물 카드는 Character와 같은 대상을 가리키고, 로어북은 인물 외에 장소·조직·물건·용어를 포함한다. 로어북 속성은 장면별 추출에서 근거 장면 ID와 함께 받아 두었다가 로어북 생성 노드에서 대상별로 모은다.

**관계 분류 (Relation.type과 label)**

| 대분류(type) | 포함하는 관계 |
| --- | --- |
| 가족 | 부모·자식, 형제, 친척 |
| 연애·혼인 | 연인, 부부, 짝사랑 |
| 협력·동료 | 친구, 동료, 파트너 |
| 위계·소속 | 스승-제자, 상관-부하, 주인-하인 |
| 적대·갈등 | 원수, 경쟁자, 대립 |
| 기타·중립 | 아는 사이, 분류하기 애매한 경우 |

type은 위 6개 중 하나로 제한하고(enum), 구체적인 내용은 label에 "스승", "의붓형제", "비밀 연인"처럼 자유 텍스트로 적는다. directed는 짝사랑이나 상관-부하처럼 한쪽에서만 성립하는 관계를 표시한다. 관계가 바뀌면(친구에서 적으로) 기존 관계를 고치지 않고 새 Relation을 since\_scene과 함께 추가한다. 화면에서는 type이 선 색과 모양, label이 호버 문구가 된다.

## FastAPI 설계

API는 "올리기 → 분석(비동기) → 결과 조회 → 질문" 네 단계로 나뉘고, 분석은 오래 걸리므로 백그라운드 작업과 진행 상황 스트리밍(SSE)으로 처리한다.

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| POST | /novels | 원고(txt) 업로드, 장면 분할·임베딩 후 novel\_id 반환 |
| POST | /novels/{id}/analyze | LangGraph 분석 시작, 즉시 job\_id 반환 |
| GET | /novels/{id}/analyze/stream | 노드 단위 진행 이벤트를 SSE로 전송 |
| GET | /novels/{id}/graph | 관계도 데이터(nodes, links) |
| GET | /novels/{id}/timeline | 사건 목록(장면 순서)과 장소 레인 목록 |
| GET | /novels/{id}/lore | 로어북 항목 목록, category로 분류 필터 |
| GET | /novels/{id}/lore/export | 로어북 전체를 분류별 마크다운(.md) 파일로 다운로드 |
| GET | /novels/{id}/scenes/{scene\_id} | 근거 장면 원문과 앞뒤 장면 |
| POST | /novels/{id}/ask | 질의응답(장면 검색 + 그래프 이웃 확장), 답변과 하이라이트 대상 반환 |
| GET | /llm/providers | 공급사와 모델 목록(설정 파일 기반), 키 설정 여부만 표시 |
| PUT | /llm/config | 공급사·모델·API 키를 서버 메모리에 저장하고 1회 연결 테스트 후 결과 반환 |
| GET | /novels/{id}/graph/path | from, to 인물 id로 최단 관계 경로 조회(Neo4j 필요, 미연결 시 사용 불가 응답) |

질의응답 응답은 답변 문장과 함께 지도에서 강조할 요소를 알려준다. 프론트는 이 값으로 노드와 카드를 하이라이트한다.

```json
{
  "answer": "스테이플턴은 ...",
  "citations": ["s0105", "s0230"],
  "highlight": {
    "characters": ["stapleton"],
    "events": ["ev_12"],
    "lore": ["lore_07"]
  }
}
```

분석 결과는 novel\_id별 JSON 파일로 저장한다. 시연에서는 이 캐시를 읽어 즉시 화면을 띄우고, 분석 시작 장면(SSE 진행바)만 짧게 라이브로 보여준다.

## 시각화 설계

시각화는 정적 HTML 한 페이지에 상단 설정 바와 탭 3개, 우측 근거 패널, 하단 질문 채팅을 두고, 모든 지도 요소의 클릭이 근거 패널로 이어지게 설계한다.

&#91;embedded content: 화면 구성 · 설정 바, 탭 3개, 근거 패널, 질문 채팅\]

지도 요소를 누르면 근거 장면 패널이 열리고, 질문 채팅의 답변은 지도 요소를 하이라이트한다. 이 양방향 연결이 시연의 핵심 장면이다.

| 뷰 | 구현 방식 | 입력 API | 핵심 인터랙션 |
| --- | --- | --- | --- |
| 인물 관계도 | D3.js force 그래프(SVG), d3-zoom으로 확대·축소·이동 | GET /graph | 노드 드래그, 노드 클릭 시 연결된 관계만 강조, 선 호버 시 세부 라벨, 선 클릭 시 근거 장면, 두 인물을 골라 최단 경로 강조(Neo4j), 휠 확대·축소와 드래그 이동, 화면에 맞추기 버튼 |
| 사건 타임라인 | D3 스윔레인: 세로 = 장면 순서, 가로 = 장소 레인(상위 8곳 + 기타·미상) | GET /timeline | 인물을 고르면 동선 선 표시, 레인 접기, 카드 클릭 시 원문 |
| 로어북 | 분류 탭과 검색창이 있는 카드 그리드(HTML) | GET /lore | 카드 클릭 시 상세와 근거 장면, 내려받기 버튼으로 마크다운 저장 |
| 질문 채팅 | 입력창과 인용 장면 칩 | POST /ask | 응답의 highlight 값으로 위 3개 뷰의 요소를 강조 |
| LLM 설정 | 상단 설정 바: 공급사 드롭다운, 모델 드롭다운, 비밀번호 형식 API 키 입력창 | GET /llm/providers, PUT /llm/config | 저장 시 연결 테스트 결과 표시, 키가 없으면 분석 시작 버튼 비활성 |

**사건 타임라인 레이아웃**

&#91;embedded content: 사건 타임라인 레이아웃 · 장소 레인 4개, 동선 1개\]

- 세로축: 원고 속 장면 순서(order)이며 위에서 아래로 흐른다. 장 구분이 없는 원고도 장면 순서만 있으면 그려진다.
- 가로축: 장소 레인이다. 레인은 로어북의 장소 항목이고, 사건 수 상위 8곳을 처음 등장한 순서로 놓은 뒤 나머지와 장소를 알 수 없는 사건은 기타·미상 레인에 모은다.
- 카드: 사건은 해당 장소 레인의 장면 위치에 놓이고, 누르면 근거 장면 패널이 열린다.
- 동선: 인물을 고르면 그 인물이 참여한 사건만 강조하고, 카드를 장면 순서대로 잇는 선이 레인 사이를 오가며 이동 경로를 그린다.
- 한계: 세로축은 이야기 속 시간이 아니라 원고 순서라서 플래시백은 보정하지 않는다. 시간순 정렬 토글은 확장 항목이다.

**관계도 데이터 포맷** (GET /graph, 값은 예시)

```json
{
  "nodes": [
    { "id": "holmes", "name": "Sherlock Holmes", "scene_count": 12, "first_scene": "s0001" }
  ],
  "links": [
    { "source": "holmes", "target": "watson", "type": "협력·동료", "label": "파트너", "directed": false, "since_scene": "s0003", "evidence": ["s0003"] }
  ]
}
```

**관계 선 표현**

| 대분류(type) | 색 | 선 모양 | 선 중앙 기호 |
| --- | --- | --- | --- |
| 가족 | 파랑 #1F77B4 | 실선 | 없음 |
| 연애·혼인 | 보라 #8E44AD | 실선 | 하트 |
| 협력·동료 | 초록 #2CA02C | 실선 | 없음 |
| 위계·소속 | 황금색 #E6A100 | 실선 | 없음 |
| 적대·갈등 | 진한 빨강 #C0392B | 굵은 점선 | ✕ |
| 기타·중립 | 회색 #8C8C8C | 가는 실선 | 없음 |

색만으로 구분하면 헷갈리기 쉬우므로 연애·혼인은 하트 기호로, 적대·갈등은 굵은 점선과 ✕ 기호로 한 번 더 구분한다. 분홍과 빨강처럼 가까운 색은 쓰지 않았지만 파랑과 보라는 비슷해 보일 수 있어 연애·혼인에 하트를 붙였다. 위 색상 값은 시작값이며, 실제 화면에서 6색을 나란히 놓고 확인한 뒤 헷갈리면 조정한다.

**관계도 화면 조작**

- 확대·축소: 마우스 휠(터치는 핀치)로 확대·축소하고, 배율은 0.2배에서 4배까지로 제한한다. 관계도 모서리에 +, −, 화면에 맞추기 버튼을 둔다.
- 화면 이동: 빈 곳을 드래그하면 화면이 이동하고, 노드를 드래그하면 그 노드만 움직인다. 확대한 상태에서도 화면 밖 노드로 이동할 수 있다.
- 전체 보기: 토글을 켜면 모든 인물이 한 화면에 들어오도록 화면에 맞추기를 자동으로 실행하고, 이후 직접 확대·이동할 수 있다.
- 라벨 표시: 축소했을 때는 이름이 겹치지 않도록 등장 장면 수 상위 인물의 이름만 보여주고, 확대하면 나머지 이름이 나타난다.
- 범례: 관계도 한쪽에 6가지 관계 범례를 두고, 항목을 누르면 해당 관계 선만 켜고 끈다.
- 인물 찾기(여유 시): 검색창에서 이름을 고르면 그 노드가 화면 가운데로 오도록 이동하고 강조된다.

**디자인 규칙**

- 색상: 관계 대분류 6가지(가족, 연애·혼인, 협력·동료, 위계·소속, 적대·갈등, 기타·중립)와 로어북 분류 5가지(인물·장소·조직·물건·용어)는 고정 팔레트로 통일한다. 관계 선의 색과 모양은 위의 관계 선 표현 표를 따르고, 방향이 있는 관계는 화살표로 표시한다.
- 밀도 관리: 관계도는 등장 장면 수 상위 12명만 기본 표시하고, "전체 보기" 토글로 나머지를 펼친다. 타임라인은 사건 수 상위 8개 장소만 레인으로 두고 나머지는 기타·미상 레인으로 묶는다.
- 하이라이트: ask 응답의 highlight에 들어 있는 요소는 강조색으로, 나머지는 흐리게 표시한다.
- 오프라인 대비: D3.js는 CDN이 아니라 web/js 폴더에 파일로 넣어 네트워크 없이도 뜨게 한다.

## 기술 스택과 폴더 구조

빌드 단계 없이 4일 안에 끝내는 것을 우선해, 백엔드는 FastAPI 한 프로세스에 프론트 정적 파일까지 함께 서빙한다.

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| API 서버 | FastAPI, Uvicorn, Pydantic v2 | 비동기·SSE 지원, 스키마가 곧 문서 |
| 파이프라인 | LangGraph | 추출→정규화→검증 흐름과 조건부 재시도를 그래프로 표현 |
| LLM | 공급사 선택형 LLM API(기본 Claude Haiku 5.5), 구조화 출력 | 노드별로 Pydantic 스키마에 맞는 JSON을 받는다 |
| 벡터DB·임베딩 | Chroma, bge-m3(로컬 임베딩) | 로컬 설치만으로 동작, 임베딩에 API 키가 필요 없다 |
| 프론트 | 정적 HTML + D3.js | 빌드 도구 없이 FastAPI StaticFiles로 서빙 |
| 그래프 DB | Neo4j(로컬 Docker 또는 Neo4j Desktop), 파이썬 드라이버 | 관계 경로 질의와 GraphRAG, 접속 정보는 .env 환경 변수로만 받는다 |

**1일차: 장면이 검색되는 벡터DB**

## 시연 시나리오

시연은 약 6분이며, 하이라이트는 "관계 선을 누르면 원문 근거가 열리는 순간"과 "마크다운 설정집 내려받기" 두 장면이다.

1. **문제 제시 (30초)**: "긴 소설의 인물 관계와 설정을 작가 본인도 전부 기억하기 어렵습니다."
2. **업로드와 분석 (1분)**: 설정 바에서 공급사·모델을 고르고 API 키를 입력한 뒤 원고를 올리면 SSE 진행바에 장면 분할, 추출, 정규화, 로어북 생성, 검증 노드가 차례로 켜진다. 이후 사전 분석한 캐시 결과로 이어서 진행한다.
3. **인물 관계도 (1분)**: 인물 노드가 퍼져 나가는 애니메이션을 보여주고, 주요 인물을 눌러 연결된 관계만 강조하고, 전체 보기에서는 확대·이동으로 화면 밖 인물까지 찾아본다. 선을 누르면 근거 장면이 열리고, 두 인물을 골라 둘 사이의 최단 경로를 강조한다(Neo4j).
4. **사건 타임라인 (1분)**: 사건 카드가 장소 레인을 따라 세로로 흐르는 화면에서 한 인물을 고르면, 그 인물의 동선 선이 레인 사이를 오가며 이어지는 것을 보여준다.
5. **로어북 (1분)**: 분류 탭과 검색으로 카드를 찾고, 카드를 눌러 속성과 근거 장면을 보여준다. 내려받기 버튼으로 마크다운 설정집을 저장해 바로 열어 보인다.
6. **질의응답 (1분)**: 예상 질문 하나를 던지면 답변과 함께 지도의 관련 노드와 카드가 깜빡이며 강조된다.
7. **마무리 (30초)**: LangGraph 파이프라인 그림 한 장으로 구조를 설명한다.

**시연 전 점검**

- [ ] 분석 결과 JSON 캐시가 있고, 네트워크 없이도 지도 2종과 로어북이 뜬다.
- [ ] 질의응답 예상 질문 3개를 미리 돌려 답변을 캐시해 둔다.
- [ ] 내려받은 마크다운 파일이 열리고 항목이 비어 있지 않다.
- [ ] Neo4j가 켜져 있고 경로 찾기가 응답하며, 꺼져 있어도 JSON 모드로 화면이 뜬다.
- [ ] API 키는 화면 공유 전에 입력해 두고, 입력창이 마스킹돼 있는지 확인한다.
- [ ] 실패 대비용 화면 녹화본을 준비한다.

## 리스크와 확장

가장 큰 위험은 인물 중복과 로어북 요약의 정확도이며, 둘 다 "근거 장면 표시"와 근거 없는 속성 제거로 신뢰를 지키는 방향으로 대응한다.

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 별칭·대명사로 인물이 중복 추출됨 | 관계도가 난잡해짐 | 정규화 노드에서 별칭 병합, 시연용은 수동 보정 JSON 허용 |
| 장소 추출·정규화가 부정확함 | 타임라인 레인이 난잡해짐 | 장소는 로어북 장소 항목으로 정규화(별칭 병합), 상위 8곳만 레인으로 표시하고 나머지는 기타·미상 레인으로 묶음 |
| 로어북 속성·요약이 원문에 없는 내용을 지어냄 | 설정집 신뢰 하락 | 속성마다 근거 장면 ID 필수, 근거 없는 속성은 검증에서 제거, 프롬프트에 근거 외 내용 금지 |
| Neo4j 설치·연동에 시간이 걸림 | 2\~3일차 지연 | Neo4j는 선택 모드로 둔다: 연결 실패 시 JSON만으로 동작하고 경로 찾기만 비활성 |
| LLM 호출 시간·비용 초과 | 10분 목표 실패 | 장면 배치 병렬 호출, 결과 캐시, 시연은 사전 분석 결과 사용 |
| API 키가 화면·로그·저장소에 노출됨 | 키 유출과 무단 과금 | 입력창 마스킹, 서버 메모리에만 보관, 로그·캐시·Git에 기록 금지(.env는 .gitignore) |
| API 호출 한도 초과 | 분석 중단 | 병렬 호출 수 제한, 429 응답 시 지수 대기 후 재시도, 장면별 결과 저장으로 이어서 실행 |
| 공급사별 구조화 출력 방식 차이 | 일부 공급사에서 JSON 오류 증가 | 차이는 어댑터 안에서 처리하고 Pydantic 검증과 재시도 엣지는 공통으로 사용 |
| 구조화 출력 JSON 오류 | 노드 중단 | Pydantic 검증 실패 시 재시도 엣지(최대 2회) |
| D3 시각화가 일정을 잡아먹음 | 3일차 지연 | 관계도를 먼저 완성하고, 타임라인·로어북은 카드형 HTML로 단순화 |
| 질의응답 응답 지연 | 시연 중 정지 | 예상 질문 답변을 미리 캐시 |
| 인물이 많아 전체 보기에서 노드가 화면 밖으로 나가거나 겹침 | 일부 인물을 확인할 수 없음 | 확대·축소·이동과 화면에 맞추기 제공, 축소 시에는 상위 인물 라벨만 표시 |
| 관계 선 색이 비슷해 관계 유형이 헷갈림 | 관계도를 읽기 어려움 | 색과 함께 선 모양·중앙 기호를 쓰고, 6색을 실제 화면에서 확인해 조정, 범례로 관계별 켜기·끄기 |

**이후 확장 아이디어**

- 이야기 속 시간순 정렬: 타임라인에 토글을 달아 플래시백을 시간순으로 재배치한다.
- Cypher 생성 질의: 자연어 질문을 LLM이 Cypher로 바꿔 그래프에 직접 질의한다.
- 복선 회수 판정: 후보 추출과 회수 판정을 분리하고, 판정 노드만 상위 모델로 추가한다.
- 로어북 편집: 작가가 카드를 직접 고치면 내보내기에 반영한다.
- 장면 슬라이더: 슬라이더를 움직이면 관계도가 시간에 따라 변한다.
- 설정 충돌 검수: 새로 쓴 문단이 기존 지도와 모순되는지 점검한다.
- 캐릭터 인터뷰어: 지도의 인물과 직접 대화한다.
